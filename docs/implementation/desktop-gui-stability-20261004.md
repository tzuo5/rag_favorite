# 桌面控制台稳定性检查与修复

检查日期：2026-10-04，America/Chicago。针对模型名称过时、点击后桌面提示无响应，检查了实时数据来源、表格刷新、线程、控制锁、关闭和断连恢复。

## 检查结果

| 问题 | 已验证的原因 | 修复 |
| --- | --- | --- |
| CCR 显示旧模型 | 界面直接显示视频 TOML 的请求别名 `Codex API/gpt-6.1-sol`，没有读取 Router 的路由改写 | 每次刷新调用本机 Router 只读管理接口，匹配当前请求的规则，显示模型、思考强度、来源与读取时间 |
| 点击与刷新无响应 | 表格在每次快照后重建全部单元格，并反复自动计算列宽；207 条任务即可阻塞主线程约 11 秒 | 复用单元格，只更新变化的值；数据未变时跳过重画；取消反复自动测宽，列宽可拖动 |
| 操作可能长期等待 | 控制文件锁使用无上限的阻塞等待 | GUI 写入最多等待 3 秒，超时报告操作未完成，保留原有暂停状态 |
| 关闭窗口等待后台读取 | 关闭请求等后台线程结束后才关闭可见窗口 | 立即隐藏，停止后续刷新，当前后台操作结束后安全退出；重新打开可以恢复显示 |
| 数据失效时模型状态不明确 | 数据库失败后模型卡片还保留正常状态 | 保留数据同时将模型标为“信息过时”；禁用危险操作，重新连接后恢复实时状态 |

此外，将后台回调明确设为 Qt 主线程的排队槽，移除覆盖 `QObject.thread()` 的同名属性；表格批量更新用 `finally` 恢复信号与绘制状态。

## 模型信息核验

本机 Router 的认证管理接口确认网关正在运行且与视频配置端点一致。
当前启用的规则匹配包含 `gpt-` 的请求，将模型改为 `codex-api/gpt-6-luna`，并将 `request.body.reasoning.effort` 设为 `xhigh`。
新版窗口实际显示 **gpt-6-luna / X-HIGH**，来源为“Router 实时路由”，并显示更新时间。

管理接口按刷新周期重新读取，测试验证运行期间修改模型和思考强度后无需重启。
接口离线、网关端点不匹配、未知条件或动态脚本无法确定时显示不可用，不会用旧请求别名冒充实时模型。
这是下一次请求匹配的当前配置路由；实际推理成功、额度与回退结果需要单独的请求证据。
检查没有发送模型推理请求，也没有修改 Router 的模型或认证设置。

## 验证与证据

- 105 项相关测试通过：控制文件锁、真实 HTTP Router 更新与异常、原生 GUI 2000 条任务压力、Start / Stop、筛选、选择保持、快速重复刷新、读取失败与恢复、慢操作期间关闭，以及真实 PostgreSQL 隔离知识库的暂停 / 恢复 / 重试与既有视频回归测试。

- 性能记录中，修复前离屏运行的 30.22 秒里 `QTableWidget.setItem` 累计占 25.71 秒；后台快照平均约 0.03 秒。卡顿发生在界面更新，而非 PostgreSQL 读取。
- 原生窗口截图保存于桌面 `RAG-GUI-实际界面.png`。
- 原始性能数据：`.runtime/gui/baseline.prof`；原生验收：`.runtime/gui/stability-after.json` 和 `.runtime/gui/stability-after.log`。
- Ruff 与 `git diff --check` 通过。
- 从桌面启动器重新打开成功，重复打开复用单一窗口；本地窗口唤起响应已验证，记录在 `.runtime/gui/desktop-activation-fixed.json`。项目目录迁移后遗留的 GUI 命令入口路径也已重新安装校正。

检查期间真实队列保持运行，worker PID `346958` 未变；本次修复仅重新打开 GUI，不重启正在处理任务的 worker。
启动日志里的 Qt host portal 注册警告在窗口正常响应时仍存在，不能将它当成本次卡顿的根因。

这轮验证覆盖控制台与队列控制。已有任务的 `EmbeddingError`、`CCR_RESPONSE_TRUNCATED` 等处理错误仍按实际状态显示，不属于窗口卡顿修复。
