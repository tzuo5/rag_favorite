## 1. Scope

The first database migration will be additive.

It must:

- preserve `public.rag_documents`;
- preserve `public.rag_chunks`;
- preserve existing ingestion, `rag_search`, and `rag_status`;
- add governed-memory storage beside the document/chunk model;
- expose no new OpenClaw or MCP mutation tools;
- perform no data migration from existing document tables.

## 2. Separation of concerns

Existing tables remain the imported-knowledge subsystem:

- `rag_documents`
- `rag_chunks`

New tables form the governed durable-memory subsystem:

- `rag_memories`
- `rag_memory_revisions`
- `rag_memory_events`

Ordinary imported documents and personal/project memories will not share one physical identity table in the first migration.

## 3. Lifecycle model

Memory lifecycle status belongs to `rag_memories`.

Allowed initial values:

- `candidate`
- `active`
- `archived`
- `rejected`

Embedding state belongs to individual revisions, not to the memory lifecycle.

Allowed initial embedding states:

- `pending`
- `ready`
- `failed`
- `not_required`

This deliberately avoids treating `pending_embedding`, `failed`, or `superseded` as memory lifecycle states.

A revision is historical when it is no longer referenced by the memory's current revision pointer.

## 4. Proposed `rag_memories`

Purpose:

- stable logical identity;
- current lifecycle state;
- current-version pointer;
- archive metadata;
- timestamps and actors.

Proposed columns:

| Column | Type | Rules |
|---|---|---|
| `id` | `UUID` | Primary key; generated by application code |
| `namespace` | `TEXT` | Constrained namespace |
| `memory_type` | `TEXT` | Non-empty semantic type |
| `status` | `TEXT` | Lifecycle constraint |
| `current_version` | `INTEGER` | At least 1 |
| `current_revision_id` | `UUID` | Must identify this memory's current revision |
| `created_by` | `TEXT` | Non-empty actor |
| `updated_by` | `TEXT` | Non-empty actor |
| `created_at` | `TIMESTAMPTZ` | Defaults to transaction time |
| `updated_at` | `TIMESTAMPTZ` | Defaults to transaction time |
| `archived_at` | `TIMESTAMPTZ` | Required only while archived |
| `archived_by` | `TEXT` | Required only while archived |
| `archive_reason` | `TEXT` | Required only while archived |
| `metadata` | `JSONB` | Object, default `{}` |

Allowed initial namespaces:

- `personal_memory`
- `project_memory`
- `knowledge_documents`
- `agent_observations`
- `quarantine`

Required invariants:

- an archived memory has all archive fields populated;
- a non-archived memory has all archive fields null;
- `current_version` and `current_revision_id` identify the same revision;
- no empty logical memory record exists without an initial revision.

## 5. Proposed `rag_memory_revisions`

Purpose:

- immutable content history;
- source provenance;
- trust classification;
- embedding data;
- version chain.

Proposed columns:

| Column | Type | Rules |
|---|---|---|
| `id` | `UUID` | Primary key; generated by application code |
| `memory_id` | `UUID` | Foreign key to `rag_memories` |
| `version` | `INTEGER` | Positive and unique per memory |
| `content` | `TEXT` | Non-empty |
| `content_hash` | `TEXT` | Lowercase SHA-256 hexadecimal |
| `source_type` | `TEXT` | Constrained provenance class |
| `source_ref` | `TEXT` | Optional bounded reference |
| `trust_level` | `TEXT` | Constrained trust class |
| `reason` | `TEXT` | Non-empty mutation reason |
| `created_by` | `TEXT` | Non-empty actor |
| `created_at` | `TIMESTAMPTZ` | Defaults to transaction time |
| `supersedes_revision_id` | `UUID` | Previous revision when applicable |
| `embedding_status` | `TEXT` | Separate from lifecycle |
| `embedding_model` | `TEXT` | Required when embedding is ready |
| `embedding_dimensions` | `INTEGER` | Must equal 1024 when embedded |
| `embedding` | `VECTOR(1024)` | Revision-specific vector |
| `metadata` | `JSONB` | Object, default `{}` |

Allowed source types:

- `user_explicit`
- `user_implicit`
- `agent_inference`
- `external_document`
- `tool_output`
- `system_generated`

Allowed trust levels:

- `untrusted`
- `low`
- `medium`
- `high`

Required invariants:

- unique `(memory_id, version)`;
- version 1 has no superseded revision;
- later versions reference the immediately previous revision;
- ready embeddings require model, dimension 1024, and vector;
- pending, failed, or not-required revisions contain no vector;
- revision rows cannot be updated or deleted through normal application roles;
- foreign keys use restrictive deletion behavior.

## 6. Proposed `rag_memory_events`

Purpose:

- immutable audit trail;
- retry idempotency;
- actor, reason, and source tracking;
- old/new state references without duplicating full memory content.

Proposed columns:

| Column | Type | Rules |
|---|---|---|
| `id` | `BIGINT GENERATED ALWAYS AS IDENTITY` | Primary key |
| `memory_id` | `UUID` | Foreign key to memory |
| `revision_id` | `UUID` | Related revision when applicable |
| `event_type` | `TEXT` | Constrained operation |
| `actor` | `TEXT` | Non-empty |
| `source_ref` | `TEXT` | Optional request/session reference |
| `reason` | `TEXT` | Non-empty |
| `idempotency_key` | `TEXT` | Globally unique and non-empty |
| `old_state` | `JSONB` | Metadata, IDs, versions, hashes and status only |
| `new_state` | `JSONB` | Metadata, IDs, versions, hashes and status only |
| `created_at` | `TIMESTAMPTZ` | Defaults to transaction time |

Allowed initial event types:

- `create`
- `update`
- `archive`
- `restore`
- `promote`
- `reject`
- `embedding_succeeded`
- `embedding_failed`

Required invariants:

- event rows are immutable;
- one event is committed for every governed mutation;
- when `revision_id` is present, it belongs to the same `memory_id`;
- full memory content is not copied into event state JSON;
- a repeated idempotency key returns the original operation result;
- conflicting reuse of an idempotency key is rejected.

## 7. Optimistic concurrency

A versioned update must:

1. receive `expected_version`;
2. insert revision `expected_version + 1`;
3. update `rag_memories` only where `current_version = expected_version`;
4. update the current revision pointer in the same transaction;
5. insert the audit event in the same transaction;
6. roll back the entire transaction when the guarded update affects zero rows.

The database transaction, not a prior application read, determines whether the update succeeds.

## 8. Immutability controls

The migration draft should include trigger-based guards rejecting:

- `UPDATE` on `rag_memory_revisions`;
- `DELETE` on `rag_memory_revisions`;
- `UPDATE` on `rag_memory_events`;
- `DELETE` on `rag_memory_events`.

Administrator recovery remains possible only through an explicit privileged maintenance procedure.

## 9. Index direction

Initial indexes:

- memory status and namespace;
- memory namespace, type, and status;
- revisions by memory and descending version;
- revisions by content hash;
- events by memory and descending creation time;
- unique event idempotency key.

No approximate vector index is required in the first migration because the governed-memory table initially contains no rows.

Vector-index selection will be deferred until row count and query behavior justify it.

## 10. Migration transaction

The SQL migration must:

1. acquire an advisory transaction lock;
2. start an explicit transaction;
3. fail if any target table already exists unexpectedly;
4. create tables, constraints, indexes, functions, and triggers;
5. add the validated current-revision foreign-key relationship;
6. write a schema-migration record or equivalent version marker;
7. commit only after all statements succeed.

It must not alter or drop the two existing RAG tables.

## 11. Rollback direction

The rollback draft must:

1. refuse destructive rollback when governed-memory rows exist unless an explicit administrator override is supplied;
2. drop immutable-event triggers;
3. drop immutable-revision triggers;
4. drop related trigger functions only when unused;
5. drop `rag_memory_events`;
6. remove the current-revision foreign-key relationship;
7. drop `rag_memory_revisions`;
8. drop `rag_memories`;
9. remove the migration version marker;
10. leave `rag_documents` and `rag_chunks` untouched.

## 12. Phase 5.1 acceptance criteria

Before production execution:

- migration SQL has a matching rollback SQL file;
- both files pass PostgreSQL parsing in a disposable database;
- no current production schema fingerprint changes during drafting;
- no MCP tool list changes;
- no OpenClaw configuration changes.

After eventual production execution:

- existing document count remains 4;
- existing chunk count remains 4;
- existing search smoke test passes;
- all three governed-memory tables exist and are empty;
- lifecycle, provenance, hash, version, embedding, and JSON constraints pass;
- revision and event immutability tests pass;
- rollback instructions are recorded but not automatically executed.
